[!!] 1.1  КОНВЕРСИИ «МС» ОТСУТСТВУЮТ В JS — ПОДПИСИ ВРУТ

 Что не так:
   В rom_editor.py в таблице CONV есть преобразования:
       lat01  -> x * 0.01 мс
       msraw  -> мс
   В J30_редактор.html в функциях rawToPhys (стр. ~165) и physToRaw
   (стр. ~177) этих ключей НЕТ. Они проваливаются в `default: return x`.

 Последствие:
   0x7F88  «Задержка форсунки», conv=lat01  -> подписано в мс, показывает БАЙТ
   0x7E20  «Пусковое обогащение», conv=msraw -> подписано в мс, показывает БАЙТ

   При этом калькулятор форсунок на той же странице пишет
       0x7F88 = введённые_мс * 100
   То есть калькулятор работает в миллисекундах, а ручной ввод — в байтах,
   и подпись поля говорит «мс» в обоих случаях.

 Риск: пользователь вводит 0.75 вместо 75. Задержка форсунки уходит в ноль.

 Что сделать (один из вариантов, выбрать):
   (а) добавить lat01 и msraw в rawToPhys/physToRaw в HTML — тогда поля
       заработают в мс, как и подписано;
   (б) снять подпись «мс» с этих параметров и показывать честный сырой байт,
       а мс писать только в note.

 ВАЖНО: масштаб «единица -> мс» для 0x7F88 и 0x7E20 в базе знаний помечен
 как ОЦЕНКА (интерпретация M30, x0.01), из кода J30 он НЕ выведен. Поэтому
 вариант (б) честнее. Если делать (а) — рядом обязательна пометка «оценка».

 Сверить: j30/база знаний/Замена форсунок — что править в прошивке 17.07.26 ИИ.txt

 там прямо написано «раньше ошибочно звалось Idle Target RPM».

 Предлагаемая подпись:
   «Опора оборотов для стабилизатора ХХ ПО УГЛУ (не цель ХХ!)»

[!] 3.4  Ориентация карт — ПРОВЕРИТЬ ОТРИСОВКУ

 Доказано кодом (FUN_80CF): смещение = обороты*16 + нагрузка.
   СТРОКИ (каждые 16 байт) = ОБОРОТЫ
   СТОЛБЦЫ (внутри строки) = НАГРУЗКА
   Максимальная нагрузка — ПРАВЫЙ столбец, НЕ верхняя строка.

 В DEFS у 0x7D00 стоит rax=0x7B00 (ось RPM) и cax=0x7AF0 (ось TP) — это
 ПРАВИЛЬНО. У 0x7C00 rax=0x7B20, cax=0x7B10 — тоже правильно.
 НО: надо глазами проверить, что рендер действительно кладёт rax в строки,
 а не наоборот. Все ранние разборы в базе, где «строки = TP», — неверны,
 и если редактор делался по ним, ошибка могла попасть в отрисовку.

[+] 5.5  СЕМЕЙСТВО 0x79A0 — ПРОВЕРИТЬ ПОДПИСЬ

 Заведено (4 секции: 0x79A0/B0/C0/D0), но НАДО СВЕРИТЬ НАЗВАНИЕ.
 Ранние файлы базы называли это «трекинг детонации, ветка инертна» — ЭТО
 ОПРОВЕРГНУТО. На самом деле это КОЭФФИЦИЕНТ ИНЕРЦИОННОГО ФИЛЬТРА ОСИ
 НАГРУЗКИ:
     $1482 += (k/256) * ($1413 - $1482)
 Выбор таблицы по оборотам $1460:
     >=36 -> 0x79A0 (> ~1850 об)
     >=24 -> 0x79B0 (~1230-1850)
     >=12 -> 0x79C0 (~615-1230)
     <12  -> 0x79D0 (< ~615)
 Внутри каждой 16-байтной строки ДВЕ подтаблицы по 8, выбор по флагу $B0.5.
 Ось внутри = нагрузка $14A2, индекс = min(2*$14A2,112)>>4.
 Смысл k: 255 = мгновенно, 32 = 12.5%/цикл, 4-8 = 1.5-3%/цикл.
 В редакторе для этого уже есть разметка оси ld8x2 — проверить, применена ли.

     ОГОВОРКА: это вольты НА НОГЕ АЦП, а не на датчике — у каждого канала
     своя обвязка. Для лямбды это как раз то, что нужно (прямой канал).

 (б) usec5 — время через тик 5 мкс.
     мс = значение * 0.005
     Применять ТОЛЬКО там, где величина действительно попадает в регистры
     UPP. Для 0x7F88 и 0x7E20 НЕ ПРИМЕНЯТЬ — их путь до регистра проходит
     через масштабирование, которое не выведено (см. баг 1.1).

 (в) Для напряжения борта: 175 отсчётов ~ 14 В -> ~0.08 В/отсчёт
     (делитель ~4.1:1). Подтверждено сверкой с даташитом.
     ЭТО ОЦЕНКА опорной точки, не из ПЗУ.

==============================================================================
 РАЗДЕЛ 9. ЧЕГО ДЕЛАТЬ НЕ НАДО / ОГОВОРКИ
==============================================================================

 - НЕ добавлять линию порога 0x7600 поверх карты смеси. Общность шкал
   $1482 (ось карт) и $14A2 (с чем сравнивается порог) в базе помечена как
   НЕ ДОКАЗАННАЯ. Нужна дотрассировка $1492 и $14A0.

 - НЕ выводить «мс» для 0x7F88 / 0x7E20 без пометки «оценка» — масштаб из
   кода J30 не выведен, это интерпретация M30 (x0.01).

 - НЕ трогать при замене форсунок: карту смеси 0x7D00, VQ 0x7A70,
   ограничители 0x7E80/0x7E90 (они сами масштабируются в Tp).

 - Формула AFR (1881.6/(X-64) и /(X+128)) взята из M30-XDF, из кода J30 НЕ
   выведена, и в районе 14.5-14.7 прыгает не в тот кластер. В редакторе есть
   режим сырого байта — для этой зоны он обязателен.

 - Формулы осей (x50 для оборотов, x0.125 для нагрузки) и температуры
   (X-50) тоже из M30-XDF, не из кода J30.

 - База ХХ 0x34B4: формула (64+X)*7.2 — ЛЕГАСИ из M30, не перепроверялась.
   Эмпирически подтверждена (пользователь менял 0x40 -> 0x2F, ХХ упал).
